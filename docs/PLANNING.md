# План разработки прототипа учёта расходов

## 1. Цель и стратегия

За два часа получить воспроизводимый веб-прототип, который полностью проходит обязательный сценарий из `ONTOLOGY.md`. Приоритет определяется оцениванием ТЗ:

1. работающий сценарий — 30 баллов;
2. точность расчётов — 30 баллов;
3. надёжность — 15 баллов;
4. удобство — 15 баллов;
5. сдача и документация — 10 баллов.

До прохождения обязательного сценария запрещено тратить время на бюджет, графики, экспорт, получателей и другие дополнительные функции: они не повышают максимальный балл.

## 2. Предлагаемая минимальная архитектура

Стек приложения:

- React
- TypeScript
- Vite

```text
/
├── src/            # веб-интерфейс и бизнес-логика
├── test/           # автоматические тесты
├── docs/
│   ├── ONTOLOGY.md
│   ├── PLANNING.md
│   └── TASKS.md
├── package.json    # зависимости и стандартные npm-команды
└── README.md
```

- Обычное веб-приложение вместо Telegram Mini App: оно не требует заранее подготовленного бота.
- Стек приложения: React, TypeScript и Vite.
- Backend отсутствует: все функции выполняются в браузере.
- Один массив `Expense` в приложении — источник истины.
- Фильтрация и все итоги вычисляются из этого массива для выбранного месяца.
- `localStorage` сохраняет только расходы; база данных отсутствует.
- Стандартный корневой скрипт `npm run dev` запускает Vite после установки зависимостей.

Дополнительные библиотеки следует выбирать по принципу минимального набора. Их выбор не должен менять модель и критерии из `ONTOLOGY.md`.

## 3. Распределение времени

| Интервал    | Этап                            | Резервный результат                                                  |
| ----------- | ------------------------------- | -------------------------------------------------------------------- |
| 00:00–00:15 | Структура и запуск              | Приложение стартует стандартной корневой командой                    |
| 00:15–00:35 | Модель, хранение и расчёты      | Есть чистые операции загрузки, сохранения, фильтрации и суммирования |
| 00:35–01:00 | Форма и валидация               | Корректный расход добавляется, неверный отклоняется                  |
| 01:00–01:20 | Список, удаление, месяц и итоги | Полный обязательный интерактивный сценарий работает                  |
| 01:20–01:35 | Надёжность и удобство           | Пустое состояние, понятные ошибки, единая валюта                     |
| 01:35–01:50 | Сквозная проверка и исправления | Официальный сценарий и обновление страницы проходят                  |
| 01:50–02:00 | README и чистый запуск          | Репозиторий воспроизводим по инструкции                              |

Если этап занимает больше времени, сокращается только косметическая полировка. Обязательный сценарий, точность, сохранение и воспроизводимость не сокращаются.

## 4. Последовательные этапы

### Этап 0. Зафиксировать спецификацию

**Зависимости:** нет.

**Работы:** согласовать `ONTOLOGY.md`, этот план и исполняемый backlog. Не начинать код до отдельного подтверждения плана.

**Ожидаемый результат:** единые сущности, инварианты, критерии приёмки, допущения и порядок реализации.

**Проверка:** три файла в `docs/` существуют, написаны на русском, согласованы между собой и не содержат дополнительного функционала в обязательном scope.

### Этап 1. Подготовить минимальный каркас и единый запуск

**Зависимости:** подтверждённый этап 0.

**Работы:** создать в корне приложение на React, TypeScript и Vite, подготовить `package.json` и стандартную команду `npm run dev`. Backend не создавать.

**Ожидаемый результат:** каркас веб-приложения запускается из корня и открывается в браузере.

**Проверка:** после установки зависимостей выполнить документируемую корневую команду и убедиться, что интерфейс доступен.

### Этап 2. Реализовать модель данных, хранение и чистые вычисления

**Зависимости:** этап 1.

**Работы:** определить `Expense`, версионированный ключ `localStorage`, безопасную загрузку/сохранение, фильтр по `YYYY-MM`, общий итог и группировку по категориям. Не хранить вычисляемые итоги.

**Ожидаемый результат:** один источник истины; для заданного массива расходов вычисления детерминированно возвращают корректные месячные итоги.

**Проверка:** на данных `1500 Еда`, `600 Транспорт`, `900 Еда` в одном месяце получить общий итог `3000`, `Еда = 2400`, `Транспорт = 600`; для другого месяца получить `0`.

### Этап 3. Реализовать форму и валидацию

**Зависимости:** этап 2.

**Работы:** добавить поля суммы, категории, даты и описания; реализовать правила `VAL-01`–`VAL-06`; при успехе создавать уникальную запись и сохранять её.

**Ожидаемый результат:** корректные расходы добавляются, некорректные не меняют данные, пользователь понимает причину отказа.

**Проверка:** отдельно проверить пустую, нулевую, отрицательную и нечисловую сумму, пустую категорию, пустую дату и корректный ввод без описания.

### Этап 4. Реализовать обязательное отображение и взаимодействие

**Зависимости:** этап 3.

**Работы:** добавить выбор месяца, список всех расходов выбранного месяца, кнопку удаления, общий итог и разбивку по категориям. Все представления строить из одного актуального состояния.

**Ожидаемый результат:** добавление, удаление и смена месяца немедленно и согласованно меняют список и итоги.

**Проверка:** добавить записи в два месяца, переключить фильтр, удалить одну запись и проверить `INV-05`–`INV-10`.

### Этап 5. Закрыть надёжность и минимальное удобство

**Зависимости:** этап 4.

**Работы:** добавить понятное пустое состояние, единообразное отображение валюты, читаемые подписи и ошибки; проверить безопасное поведение при отсутствии или некорректном значении хранилища.

**Ожидаемый результат:** интерфейс понятен, пустой месяц не выглядит ошибкой, приложение не падает при первом запуске.

**Проверка:** открыть приложение с чистым `localStorage`, проверить месяц без расходов и визуально сверить валюту во всех местах.

### Этап 6. Провести обязательную сквозную проверку

**Зависимости:** этап 5.

**Работы:** пройти официальный сценарий дословно, включая обновление страницы; исправлять только дефекты обязательного сценария и критериев оценки.

**Ожидаемый результат:** подтверждены ввод, список, удаление, точность расчёта, реактивность и сохранение.

**Проверка:** чек-лист из раздела 5 выполнен полностью; сумма категорий на каждом шаге равна общему итогу.

### Этап 7. Подготовить сдачу и проверить воспроизводимость

**Зависимости:** этап 6 успешно пройден.

**Работы:** обновить корневой `README.md`: назначение, реализованные функции, ограничения, требования к окружению, установка и одна команда запуска. Затем проверить запуск в чистом состоянии зависимостей по этой инструкции.

**Ожидаемый результат:** другой проверяющий может воспроизвести проект без устных пояснений.

**Проверка:** остановить процессы, выполнить описанные в README установку и одну корневую команду запуска, открыть приложение и выполнить короткую smoke-проверку добавления, обновления страницы и удаления.

### Этап 8. Только при наличии времени после приёмки

Дополнительные функции не планируются. Оставшееся время используется на исправление ошибок, читаемость интерфейса и повтор обязательного сценария. Изменение scope возможно только после отдельного решения команды.

## 5. Официальный проверочный сценарий

Использовать один и тот же выбранный месяц и даты внутри него.

- [ ] Добавить `Еда — 1500`.
- [ ] Добавить `Транспорт — 600`.
- [ ] Добавить `Еда — 900`.
- [ ] Проверить наличие трёх записей.
- [ ] Проверить: всего `3000`, `Еда — 2400`, `Транспорт — 600`.
- [ ] Проверить: сумма категорий равна `3000`.
- [ ] Обновить страницу.
- [ ] Проверить, что три записи и итоги сохранились.
- [ ] Удалить расход `Еда — 900`.
- [ ] Проверить наличие двух записей.
- [ ] Проверить: всего `2100`, `Еда — 1500`, `Транспорт — 600`.
- [ ] Проверить: сумма категорий равна `2100`.
- [ ] Выбрать пустой месяц: список пуст, общий итог `0`.
- [ ] Вернуться в исходный месяц: оставшиеся данные и итог `2100` доступны.

## 6. Дополнительная матрица проверки требований

| Область         | Что проверить                                                      | Связанные требования                |
| --------------- | ------------------------------------------------------------------ | ----------------------------------- |
| Валидация       | Сумма `> 0`, обязательные категория и дата, описание необязательно | `VAL-01`–`VAL-06`, `AC-01`, `AC-02` |
| Месячный фильтр | В списке и итогах только выбранный месяц                           | `BR-03`, `FR-04`, `FR-06`, `AC-03`  |
| Расчёт          | Общий итог и категории, равенство их сумм                          | `INV-05`–`INV-07`, `AC-05`          |
| Регистр категорий | `Еда`, `еда` и `ЕДА` объединяются в одну сумму                   | `BR-10`, `INV-14`, `AC-11`          |
| Пересчёт        | Добавление, удаление и смена месяца                                | `BR-06`, `FR-09`, `AC-06`           |
| Сохранение      | Записи переживают обновление страницы                              | `BR-09`, `FR-10`, `AC-07`           |
| Надёжность      | Чистое/повреждённое хранилище и пустой месяц не роняют UI          | `BR-08`, `AC-08`                    |
| Валюта          | Одинаковое обозначение, нет выбора и конвертации                   | `BR-07`, `INV-12`, `AC-09`          |
| Запуск          | Одна команда из корня после установки                              | `NFR-05`, `NFR-06`, `AC-10`         |

## 7. Условия остановки и управления рисками

- Если запуск не настроен к 00:15, приоритет — рабочий корневой скрипт Vite.
- Если UI отстаёт от графика, используется простая форма и текстовый список без визуальных украшений.
- Если обнаружена ошибка расчёта или сохранения, косметические задачи приостанавливаются до её исправления.
- Нельзя добавлять дополнительную функцию при любом непрошедшем пункте официального сценария.
- Итоги не следует хранить отдельно: это главный способ снизить риск рассинхронизации.
- Перед сдачей необходим повторный запуск строго по README, а не только в уже работающей среде разработчика.

## 8. Критерий завершения плана

План завершён, когда выполнены все задачи обязательного backlog, официальный сценарий проходит после чистого запуска, данные переживают обновление страницы, а README позволяет воспроизвести проект одной корневой командой после установки зависимостей.
