# Прикладная онтология учёта личных расходов

## 1. Назначение и границы модели

Система — однопользовательский веб-прототип для ручного учёта личных расходов студента. Пользователь создаёт и удаляет расходы, выбирает календарный месяц и видит относящиеся к нему записи, общий итог и разбивку по категориям. Расчёты выполняются только по введённым данным, а записи хранятся в браузере.

Онтология описывает только обязательный сценарий технического задания. Дополнительные функции из ТЗ не входят в план до его полного прохождения.

## 2. Сущности и атрибуты

### 2.1. Расход (`Expense`)

Основная сохраняемая сущность.

| Атрибут | Тип | Обязательность | Смысл |
| --- | --- | --- | --- |
| `id` | строка, уникальная | обязательно | Стабильный идентификатор записи для отображения и удаления |
| `amount` | конечное число | обязательно | Положительная сумма расхода в единой валюте приложения |
| `category` | строка | обязательно | Непустое название категории после удаления пробелов по краям |
| `date` | календарная дата `YYYY-MM-DD` | обязательно | Дата совершения расхода |
| `description` | строка | необязательно | Пользовательское описание; пустое значение допустимо |

### 2.2. Выбранный месяц (`SelectedMonth`)

Состояние интерфейса, задающее область списка и расчётов.

| Атрибут | Тип | Обязательность | Смысл |
| --- | --- | --- | --- |
| `value` | календарный месяц `YYYY-MM` | обязательно | Месяц, за который показываются расходы и итоги |

### 2.3. Итог месяца (`MonthlySummary`)

Вычисляемое, не сохраняемое представление.

| Атрибут | Тип | Смысл |
| --- | --- | --- |
| `month` | `YYYY-MM` | Месяц расчёта |
| `total` | число | Сумма всех расходов выбранного месяца |
| `byCategory` | отображение «категория → сумма» | Суммы расходов выбранного месяца, сгруппированные по категории |
| `expenseCount` | целое неотрицательное число | Количество записей выбранного месяца |

### 2.4. Ошибка валидации (`ValidationError`)

Временное состояние интерфейса, не сохраняемое в хранилище расходов.

| Атрибут | Тип | Смысл |
| --- | --- | --- |
| `field` | имя поля формы | Поле, которое необходимо исправить |
| `message` | строка | Понятное пользователю объяснение ошибки |

### 2.5. Пользователь (`Student`)

Единственный актор системы. Профиль, идентификатор, регистрация и авторизация отсутствуют: пользователь работает с локальными данными текущего браузера.

## 3. Связи между сущностями

- Пользователь создаёт и удаляет `Expense`.
- `Expense` относится ровно к одному календарному месяцу, вычисляемому из `date`.
- `SelectedMonth` фильтрует множество `Expense`, видимых в списке и участвующих в расчёте.
- Один `MonthlySummary` вычисляется из всех и только тех `Expense`, дата которых относится к `SelectedMonth`.
- Каждая запись выбранного месяца участвует ровно в одной группе `byCategory`, определяемой её `category` без учёта регистра.
- `ValidationError` может относиться к одному полю формы и препятствует созданию расхода до исправления данных.

## 4. Бизнес-правила

**BR-01.** Расход создаётся только при наличии корректных суммы, категории и даты.

**BR-02.** Описание расхода необязательно.

**BR-03.** Список содержит все и только расходы выбранного месяца.

**BR-04.** Пользователь может удалить любую отображаемую запись.

**BR-05.** Общий итог и разбивка по категориям рассчитываются по расходам выбранного месяца.

**BR-06.** Итоги пересчитываются после добавления, удаления и смены выбранного месяца.

**BR-07.** Все суммы трактуются как значения одной фиксированной валюты; конвертация и курсы валют отсутствуют.

**BR-08.** При отсутствии расходов список показывает понятное пустое состояние, общий итог равен нулю, разбивка по категориям пуста.

**BR-09.** Записи должны оставаться доступными в том же браузере после обновления страницы.

**BR-10.** Названия категорий сравниваются без учёта регистра: например, `Еда`, `еда` и `ЕДА` образуют одну категорию. В итогах показывается написание первой встретившейся записи этой группы.

## 5. Правила валидации

**VAL-01. Сумма:** значение обязательно, преобразуется в число, должно быть конечным и строго больше нуля. Пустое значение, ноль, отрицательное и нечисловое значение отклоняются с понятным сообщением.

**VAL-02. Категория:** значение обязательно; строка, состоящая только из пробелов, считается пустой и отклоняется.

**VAL-03. Дата:** значение обязательно и должно представлять существующую календарную дату в формате, поддерживаемом полем даты интерфейса.

**VAL-04. Описание:** может отсутствовать или быть пустым; его наличие не влияет на допустимость расхода и расчёты.

**VAL-05. Выбранный месяц:** должен быть корректным календарным месяцем; без него нельзя сформировать месячный список и итоги.

**VAL-06. Ошибка формы:** при любой ошибке расход не создаётся, сохранённые расходы и текущие итоги не изменяются, а пользователь получает сообщение, указывающее, что исправить.

## 6. Вычисляемые значения

Для выбранного месяца `M`:

```text
monthExpenses(M) = все Expense, для которых month(Expense.date) = M
total(M) = сумма Expense.amount по monthExpenses(M)
categoryKey(C) = C, приведённая к нижнему регистру
categoryTotal(M, C) = сумма Expense.amount по monthExpenses(M), где categoryKey(Expense.category) = categoryKey(C)
byCategory(M) = categoryTotal(M, C) для каждой регистронезависимой категории C из monthExpenses(M)
expenseCount(M) = количество элементов monthExpenses(M)
```

`MonthlySummary` всегда выводится из актуального массива расходов, а не хранится как отдельный источник истины. Это исключает рассинхронизацию списка, общего итога и категорий.

## 7. Пользовательские действия и реакции системы

| Действие пользователя | Реакция системы |
| --- | --- |
| Открыть приложение | Загрузить расходы из браузерного хранилища, определить выбранный месяц, показать его список и рассчитанные итоги |
| Ввести данные и добавить корректный расход | Создать запись с уникальным `id`, сохранить её, обновить список и немедленно пересчитать итоги выбранного месяца |
| Отправить форму с неверными данными | Не создавать и не сохранять запись; показать понятное сообщение у соответствующего поля или в области ошибок |
| Удалить расход | Удалить ровно выбранную запись из состояния и хранилища; немедленно обновить список и итоги |
| Сменить месяц | Не изменять расходы; показать записи нового месяца и немедленно пересчитать общий и категорийные итоги |
| Обновить страницу | Восстановить сохранённые расходы из браузерного хранилища и снова вычислить отображаемые данные |
| Открыть месяц без расходов | Показать пустое состояние, общий итог `0` и отсутствие категорийных сумм |

## 8. Правила хранения данных

- Источник сохраняемых данных — браузерное локальное хранилище (`localStorage`) текущего браузера и origin приложения.
- Под одним версионированным ключом хранится сериализованный массив объектов `Expense`.
- Сохранение выполняется после успешного добавления и успешного удаления.
- Итоги и отфильтрованный список отдельно не сохраняются: они вычисляются из расходов.
- Серверная часть и база данных отсутствуют; расходы не отправляются во внешние сервисы.
- Обновление страницы не должно очищать данные.
- Очистка хранилища браузера, другой браузер, другой профиль или другой origin не обязаны сохранять доступ к записям.
- Если сохранённое значение невозможно прочитать как ожидаемый массив расходов, приложение должно не падать и перейти к безопасному пустому состоянию. Восстановление повреждённых данных ТЗ не требует.

## 9. Функциональные требования

**FR-01.** Форма ввода содержит сумму, категорию, дату и необязательное описание.

**FR-02.** Форма отклоняет некорректные обязательные данные с понятным сообщением.

**FR-03.** Приложение добавляет корректный расход на основании пользовательского ввода.

**FR-04.** Приложение показывает все добавленные расходы выбранного месяца списком.

**FR-05.** Пользователь может удалить расход из списка.

**FR-06.** Пользователь может выбрать календарный месяц.

**FR-07.** Приложение показывает общий итог выбранного месяца.

**FR-08.** Приложение показывает суммы выбранного месяца по категориям.

**FR-09.** Список и итоги обновляются при добавлении, удалении и смене месяца.

**FR-10.** Расходы сохраняются после обновления страницы в том же браузере.

**FR-11.** Приложение корректно отображает месяц без расходов.

## 10. Нефункциональные ограничения

**NFR-01.** Интерфейс должен быть понятен без отдельного обучения: различимы форма, выбранный месяц, список, общий итог, категории и сообщения об ошибках.

**NFR-02.** Реакция на добавление, удаление и смену месяца должна быть визуально немедленной, без ручного обновления страницы.

**NFR-03.** Расчёты должны быть детерминированы введёнными пользователем данными; заранее подготовленные итоги запрещены.

**NFR-04.** Приложение не зависит от ИИ, внешних API и сетевых источников данных.

**NFR-05.** Прототип должен запускаться одной документированной командой из корня репозитория.

**NFR-06.** Решение должно воспроизводимо запускаться по инструкции в `README.md` после установки зависимостей.

**NFR-07.** Архитектура должна оставаться минимальной и выполнимой за два часа.

## 11. Явно исключённый scope

В обязательную реализацию не входят:

- регистрация, вход, аккаунты и разграничение доступа;
- синхронизация между устройствами, браузерами или пользователями;
- серверное хранение и база данных;
- банковские интеграции, импорт операций и реальные платежи;
- ИИ и внешние API;
- конвертация валют и одновременный учёт нескольких валют;
- Telegram-бот и Telegram Mini App: выбран обычный веб-формат;
- месячный бюджет;
- графики и диаграммы;
- экспорт данных;
- отметка «на кого потратили» и итоги по получателям;
- редактирование существующего расхода;
- любые дополнительные функции до прохождения обязательного проверочного сценария.

## 12. Критерии приёмки

**AC-01. Ввод:** корректные сумма, категория и дата создают расход; описание можно не заполнять.

**AC-02. Валидация:** пустые обязательные поля, нулевая, отрицательная или нечисловая сумма не создают расход и сопровождаются понятным сообщением.

**AC-03. Список:** выбранный месяц показывает все добавленные в нём записи и не показывает записи других месяцев.

**AC-04. Удаление:** любую видимую запись можно удалить, после чего она исчезает из списка и хранилища.

**AC-05. Расчёт:** общий итог равен сумме расходов выбранного месяца, разбивка по категориям корректна, сумма разбивки равна общему итогу.

**AC-06. Реактивность:** добавление, удаление и смена месяца немедленно обновляют список и оба вида итогов.

**AC-07. Сохранение:** после обновления страницы созданные и не удалённые записи доступны и дают те же итоги.

**AC-08. Пустое состояние:** месяц без расходов отображается без ошибки с общим итогом `0`.

**AC-09. Единая валюта:** суммы в форме, списке, общем итоге и категориях оформлены в одной валюте; выбора валюты и конвертации нет.

**AC-10. Запуск и сдача:** проект запускается одной командой из корня, а `README.md` описывает запуск, функции и ограничения.

**AC-11. Регистр категорий:** расходы с названиями категорий, отличающимися только регистром, объединяются в одну категорию с общей суммой.

## 13. Официальный проверочный сценарий

1. Запустить весь проект одной командой из корня репозитория и открыть веб-приложение.
2. Выбрать один календарный месяц.
3. Добавить в этом месяце расход `Еда` на `1500`.
4. Добавить в этом же месяце расход `Транспорт` на `600`.
5. Добавить в этом же месяце расход `Еда` на `900`.
6. Убедиться, что список содержит три записи.
7. Убедиться, что общий итог равен `3000`, итог категории `Еда` — `2400`, итог категории `Транспорт` — `600`.
8. Убедиться, что сумма итогов категорий равна общему итогу.
9. Обновить страницу и убедиться, что три записи и те же итоги сохранились.
10. Удалить расход `Еда` на `900`.
11. Убедиться, что список содержит две записи, общий итог равен `2100`, итог категории `Еда` — `1500`, итог категории `Транспорт` — `600`.
12. Переключиться на месяц без расходов и убедиться, что список пуст, а общий итог равен `0`.
13. Вернуться в исходный месяц и убедиться, что оставшиеся записи и итог `2100` снова показаны.

## 14. Технические ограничения проекта

- Репозиторий должен иметь корневые папки `src/`, `test/`, `docs/`, а также корневые `package.json` и `README.md`.
- Выбран формат обычного веб-приложения.
- Приложение реализуется на React, TypeScript и Vite.
- Приложение отвечает за форму, состояние, фильтрацию, расчёты и `localStorage`.
- Backend отсутствует.
- База данных не используется.
- Внешние API и ИИ не используются.
- Весь проект запускается одной командой из корня репозитория.
- Основной источник истины для расходов — массив записей в браузере; производные итоги не дублируются в хранении.

## 15. Инварианты системы

**INV-01.** Сумма каждого сохранённого расхода — конечное число строго больше нуля.

**INV-02.** Категория каждого сохранённого расхода обязательна и не пуста после удаления внешних пробелов.

**INV-03.** Дата каждого сохранённого расхода обязательна и является корректной календарной датой.

**INV-04.** Идентификатор каждого расхода уникален среди сохранённых записей.

**INV-05.** Общий итог выбранного месяца равен сумме сумм всех и только отображаемых расходов этого месяца.

**INV-06.** Сумма итогов по категориям выбранного месяца равна общему итогу этого месяца.

**INV-07.** Каждый отображаемый расход учитывается в общем итоге и ровно в одной категории.

**INV-08.** После добавления или удаления расхода список, общий итог и категории отражают одно и то же актуальное множество данных.

**INV-09.** После удаления расход больше не участвует ни в списке, ни в общем итоге, ни в итоге категории, ни в сохранённых данных.

**INV-10.** Смена месяца не добавляет, не удаляет и не изменяет расходы.

**INV-11.** После обновления страницы все ранее сохранённые и не удалённые расходы доступны в том же браузере.

**INV-12.** Все расходы, поля сумм и итоги используют одну валюту без конвертации.

**INV-13.** Для месяца без расходов общий итог равен нулю, а категорийных итогов нет.

**INV-14.** Регистр букв не влияет на принадлежность расхода к категории и её итоговую сумму.

## 16. Неоднозначности ТЗ

- Не указаны конкретная валюта и правила её форматирования.
- Не определён список категорий и способ их ввода: свободный текст или фиксированный выбор.
- Не указаны допустимое число знаков после запятой, максимальная сумма и способ округления.
- Не задан начальный выбранный месяц и необходимость сохранять его после обновления страницы.
- Не сказано, должна ли дата нового расхода автоматически менять выбранный месяц или расход с датой другого месяца просто не появляется в текущем фильтре.
- Не определены порядок сортировки расходов и категорий.
- Не заданы максимальная длина категории и описания.
- Не описано поведение при повреждённых или вручную изменённых данных в `localStorage`.
- Все обязательные функции выполняются в браузере, поэтому отдельная серверная часть не требуется.
- Формулировка «одной командой» не уточняет, включает ли эта команда установку зависимостей; в плане установка и запуск разделены.

## 17. Допущения

Эти решения нужны для однозначной реализации и не расширяют пользовательский функционал:

- Валюта выбирается один раз на уровне приложения и одинаково отображается везде; переключателя валют нет. Конкретное обозначение фиксируется при реализации и документируется в `README.md`.
- Категория вводится как свободный текст, пробелы по краям удаляются; варианты, отличающиеся только регистром, объединяются. В итогах используется написание первой встретившейся записи группы; другие различия в написании не нормализуются.
- Денежное значение хранится как число. Специальные ограничения на десятичные значения сверх стандартного числового ввода не вводятся, поскольку их нет в ТЗ.
- При первом открытии выбран текущий локальный календарный месяц. Сам выбранный месяц можно не сохранять: требование сохранения относится к записям.
- Даты хранятся как календарные строки `YYYY-MM-DD` и относятся к месяцу по первым семи символам, без преобразования часовых поясов.
- Если дата добавленного расхода относится не к выбранному месяцу, запись сохраняется, но не включается в текущий список и итоги; пользователь увидит её после выбора соответствующего месяца.
- Порядок списка и категорий выбирается только для устойчивого понятного отображения и не влияет на расчёты.
- Повреждённое значение локального хранилища не должно приводить к падению интерфейса; допустимо безопасное пустое состояние.
- Установка зависимостей выполняется по `README.md`, после чего стандартная команда `npm run dev` запускает приложение.
